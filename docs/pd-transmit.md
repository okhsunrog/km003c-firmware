# Native PD transmit path and GoodCRC responsibilities

The HC32F460 does not expose a dedicated USB-PD/UCPD peripheral in its documented
peripheral inventory. Its USB FS controller has a USB data PHY for D+/D-, which
is separate from Power Delivery signaling on CC. The manufacturer's
[peripheral overview](https://www.xhsc.com.cn/product/1246.html) lists USB FS,
comparators, timers, DMA and AOS. Datasheet feature pages were checked through
`mistral_ocr`. KM003C implements PD using these general-purpose peripherals
plus board-level analog circuitry that is not yet fully reconstructed.

## Transmit timing is generated by hardware

The catalog 1.9.9 code uses an interval encoder in RAM at `0x1fff8184`.
`0x100d2(buffer,count)` preloads TimerA2 PERAR at `0x40015404` with the first
halfword and points DMA1 CH1 SAR to the next halfword. The DMA destination is
PERAR, and its trigger is TimerA2 overflow (`0x103`). Subsequent periods are
therefore supplied without a CPU interrupt for each edge.

The selected output is PCONR1/2 at `0x40015540/44`, routed to PA0/PA1 AF4.
Native init writes `0x00e0`. The SDK/SVD fields decode as CMPC=2 (hold at compare)
and PERC=3 (invert at period). Thus the timer toggles the output on period events;
DMA changes the time until the next event. In TX setup `0x1018c(0,handler)`, the
selected PCONR's PERC is set to 3 and OUTEN bit 12 is enabled; comparator edge
events and RX timer hardware start are disabled. RX setup clears OUTEN.

This is a software-encoded, timer/DMA-driven PHY. It does not busy-loop CPU GPIO
writes or run an interrupt for every BMC edge. The analog signal on CC also
depends on external components and PC14/PC15 control, whose exact electrical
roles remain unresolved. These findings do not authorize blindly enabling TX.

The addresses above belong to catalog 1.9.9. They must be remapped before being
used to interpret a different firmware build. They are not functions called by
the custom Rust image. Encoding, TX completion/EOP/idle handling and RX turnaround
still require implementation and physical acceptance in Rust.

## Board controls recovered from the catalog code

The following control-flow evidence is from 1.9.9; it is auxiliary until remapped
and checked against 2.0.7. Passive CC wiring and voltages are now independently
[hardware-tested](line-adc.md), but this does not establish the TX circuit.

| Control | Observed native use |
| --- | --- |
| PA0 / PA1 | CMP1_INP1/2 in RX; TimerA2 AF4 output 1/2 in TX (`0x435ae`) |
| PC14 / PC15 | Output latch, output-enable and internal pull-up change with CC mode; not merely a TX-enable pair |
| PB6 | Cleared by `0x435de`; set in mode 1/3 by `0x43610` |
| AW9523 P0_3 | High, low or high-impedance via mask `0x08` and `0x1a9c8` |
| AW9523 P1_6 | Output-latch bit changed via mask `0x40` and `0x1aa56`; that helper does not set direction |

`0x1a9c8(mask,state)` manipulates AW9523 OUTPUT0/CONFIG0: state 0 sets the
direction bit (input/high-impedance); state 1 sets the latch then enables output;
other states clear the latch then enable output. `0x1aa56(mask,state)` changes
OUTPUT1 only. Both call the I2C helper for address `0x5b`.

`0x43610` combines PB6 and P0_3: mode 0 clears PB6 and releases P0_3, mode 1 sets
PB6, mode 2 pulls P0_3 low, mode 3 does both. `0x4343c` drives the selected
PC14/PC15 low, `0x4346a` high, and `0x43416` disables its output. `0x434b6` also
changes the opposite pin's pull-up and expander outputs depending on selected
CC. These routines establish software states, not resistor values or a full
schematic. In the GPIO PCR, POUTE is bit 1, PUU bit 6 and DDIS bit 15; confusing
these would misidentify the role of the switching sequence.

Continuity/net tracing and controlled electrical measurements are still needed
to distinguish terminations, mux/driver enables and the external BMC analog
stage. The custom passive implementation does not actuate these controls.

## What auto-GoodCRC means

Published `usbpd-traits` 2.0.0 has `Driver::HAS_AUTO_GOOD_CRC`, default false.
When false, the protocol layer constructs GoodCRC and calls the driver's
`transmit`. When true, it skips that acknowledgement and expects the lower layer
to provide it. This flag describes an adapter contract; it does not indicate
that HC32 contains a dedicated hardware acknowledgement engine.

For the first HC32 adapter, leave both `HAS_AUTO_GOOD_CRC` and `HAS_AUTO_RETRY`
false and let `usbpd` provide protocol behavior. Receive must deliver validated
header/payload bytes through the fast internal path, bypassing JSON/CDC. Transmit
must encode CRC/4b5b/BMC and start timer/DMA. The existing passive PHY is not yet
such a complete TX/RX adapter.

A future lower-driver automatic acknowledgement could validate a received packet,
construct the appropriate GoodCRC header/CRC, and launch a prepared timer/DMA
waveform promptly. The adapter could only advertise that capability after it
handles role/revision/Message ID correctly, meets timing, and prevents duplicate
acknowledgements from the protocol layer. No such HC32 implementation is currently
present or hardware-accepted. Timer-driven edges alone do not guarantee response
time: RX completion, validation, scheduling, encoding and RX-to-TX turnaround
all contribute.

The measured 3.78 µs RX rearm portion is not a GoodCRC response-time measurement.
Current millisecond uptime stamps cannot establish microsecond response timing;
use cycle-level measurements and an external signal capture for TX acceptance.

Source: [driver contract](https://github.com/elagil/usbpd/blob/b21607ad8b960da56ae801c5e42d9a86485a1f81/usbpd-traits/src/lib.rs).
The same flags were verified in the locally installed crates.io 2.0.0 source,
as used by km003c-rs. No dependency switch or hardware transmission was performed.
